# Инструкции для Claude: portfolio

Общие правила — в `E:\Projects\CLAUDE.md`. Здесь только специфика этого проекта.

## О проекте

- Портфолио владельца. Remote: https://github.com/22504105/portfolio, основная ветка `main`.
- Один общий репозиторий: каждая работа — отдельная папка в корне со своим стеком и деплоем.
- **`nova-residence/`** — концепт-лендинг вымышленного ЖК в Стамбуле (Next.js 16,
  TypeScript, Tailwind v4, Motion, деплой на Vercel из подпапки).
- **`barbershop-demo/`** — CUT&CO: концепт барбершопа в Лондоне с онлайн-записью (Next.js 16,
  next-intl EN/RU, Supabase, цены в USD). Полноценное приложение с БД, а не лендинг.

## CUT&CO (barbershop-demo): постоянные инструкции

- **Источник требований** — `barbershop-demo/docs/brief.md` (Master Brief + пять фаз).
  Приоритет: бриф → `docs/architecture.md` → `docs/design-system.md` → инструкции фазы →
  решения Lead. Утверждённую в брифе политику записи молча не менять.
- **Фазы**: только та, на которую владелец дал явную команду; после фазы — отчёт и остановка.
  Ветки `cutco/phase-NN`, мерж в `main` после ревью владельца.
- **Команда**: Lead + три субагента в `.claude/agents/`: `cutco-ui`, `cutco-backend`,
  `cutco-qa`. Экономия токенов — как в NOVA: не больше одного вызова каждой роли за фазу.
  Фазы 01–03 пока сделаны Lead без субагентов.
- **База**: облачный Supabase (решение владельца 2026-10-10; Docker на машине нет). Планируются
  два проекта: рабочий и изолированное демо. Проект владелец ещё не создал.
- **Доступ к базе**: сервер ходит в PostgreSQL напрямую (`pg`, `DATABASE_URL`), правила записи —
  в функциях БД (`supabase/migrations/*booking_engine.sql`). Клиент Supabase нужен только для
  Auth. Почему — `docs/architecture.md`, раздел 11.
- **Локальная разработка без Supabase**: `npm run db:dev` поднимает PostgreSQL в `.tmp/dev-db`
  (порт 54329), применяет миграции и сиды и пишет `.env.local`. Письма не отправляются, а
  складываются в `.tmp/mail` и видны на `/en/dev/mail`. Без базы сайт работает на встроенном
  каталоге, запись — в режиме предпросмотра на моке.
- **Все пять фаз сделаны** (вход по почте и паролю — решение владельца 2026-10-11; Фаза 03
  принята им 2026-10-11 словами «everything its ok»; после Фазы 04 он попросил убрать точки в
  заголовках и уменьшить шрифт и продолжать). Фаза 05 (`cutco/phase-05`): заголовки
  безопасности, токены писем после `#`, хранение и удаление данных, PWA, проверка доступности,
  README, `docs/security.md`, `docs/case-study.md`. Ждёт ревью владельца; ветки `cutco/*` в
  `main` не смержены; **не задеплоено** — деплой только по явной команде.
- **Аудит Фазы 05 — самопроверка Lead**, не независимая (субагенты не запускались). Что не
  проверено — `docs/security.md`, «Residual risks».
- **Заголовки без точки в конце и спокойный размер** — просьба владельца 2026-10-11
  («выглядит очень агрессивно»). Новые заголовки писать так же.
- **Всё должно быть доступно с сайта** (просьба владельца 2026-10-11): у каждого раздела есть
  ссылка в интерфейсе — кабинет в шапке и мобильном меню, демо админки в подвале, переходы
  для барбера и админа со страницы кабинета. Новые страницы без ссылки не оставлять.
- **Демо админки** (`/demo/admin`) не читает базу вообще: те же страницы получают источник
  `lib/admin/demo.ts` с выдуманными данными в памяти. Реальная админка — `lib/admin/live.ts`.
- **Supabase владельца подключён** (проект `dwssavuhcagfqaolqcoi`, eu-west-1). `.env.local`
  указывает на него через Transaction pooler; миграции применены (`npm run db:migrate`).
  Это рабочая база, не тестовая: после браузерных проверок чистить за собой
  (`.tmp/qa/cleanup.mjs`). Прямой адрес `db.<ref>.supabase.co` из этой сети недоступен (только IPv6).
- **Сотрудники**: `npm run user:create -- <email> <role> [slug]` пишет напрямую в `auth.users`;
  пароль печатается один раз. Учётные записи админа и барберов владелец ещё не создавал.
- **Проверка**: `npm run typecheck`, `npm run lint`, `npm test`, `npm run build` из
  `barbershop-demo/`. `npm test` поднимает настоящий PostgreSQL (`embedded-postgres`) в
  `.tmp/`, применяет миграции и сиды.
- **Грабли**:
  - Миграции должны идти и на Supabase, и на чистом PostgreSQL с `tests/db/supabase-shim.sql`.
  - Vitest 5 требует `@types/node` 22+.
  - Bash heredoc съедает обратные слэши: файлы с регулярками писать через Write. Так был
    испорчен `matcher` в `proxy.ts` — страницы открывались, но редиректы на язык молча не
    работали; теперь это ловит `tests/proxy.test.ts`.
  - Цвета, зависящие от тона секции, объявлять в `@theme inline`, иначе Tailwind вычисляет
    их один раз на `:root`.
  - Скрытый `sr-only`-инпут без `relative` у родителя расширяет документ: в горизонтальной
    ленте дат это дало +800px ширины страницы и ломало тапы на телефоне.
  - Изображения: исходники владельца — в `barbershop-images-inbox/` (вне git), список и
    промпты — `barbershop-demo/docs/image-brief.md`, обработка —
    `npm run images -- ../barbershop-images-inbox`. Пока файла нет, `Photo` рисует пустую
    рамку с подписью.
  - `lib/catalog/index.ts` импортируют клиентские компоненты: в нём только типы и чистые
    функции. Всё, что тянет `pg` (`lib/db.ts`, `lib/catalog/server.ts`, `lib/booking/store.ts`),
    в клиент попадать не должно — иначе dev-сервер падает с «Can't resolve 'dns'».
  - Письма в production-сборке на локальной машине: `EMAIL_SINK=1` (иначе без ключа Resend
    задания падают). Для сквозной проверки: `APP_URL=http://localhost:3100 EMAIL_SINK=1 PORT=3100
    npm run start` и `.tmp/qa/live.mjs`.
  - Напоминаниям нужен планировщик раз в несколько минут; бесплатный Vercel Cron умеет только
    раз в сутки — вызывать `/api/cron/notifications` из Supabase `pg_cron` или внешнего сервиса.
  - `\b` в Python-строке внутри heredoc превращается в backspace: регулярки так не править.
  - Server action не обновляет страницу, с которой вызван, пока не вызовет `revalidatePath`
    (или не поменяет cookie / не сделает redirect): без этого список после действия не менялся.
  - `innerText` в браузерных проверках отдаёт текст с учётом `text-transform`: заголовки
    приходят заглавными, сравнивать без учёта регистра.
  - Лимиты запросов настоящие (5 броней в час на адрес): повторные прогоны проверок упираются
    в них, перед прогоном чистить `rate_limits`.
  - Пароль базы со спецсимволами (`?`, `@`, `#`) в `DATABASE_URL` нужно percent-кодировать.
  - `>>` в JS — знаковый сдвиг: на большом беззнаковом хэше даёт отрицательное число, а за
    ним отрицательный индекс и «undefined undefined» вместо имени. Для хэшей — только `>>>`.
  - Скриншоты смотреть глазами даже при зелёных проверках: «undefined» в демо-данных и
    35 % отмен нашёл просмотр, а не тесты.
  - Таблица внутри ячейки grid раздувает страницу на телефоне, пока у ячейки нет `min-w-0`.
  - Браузерные проверки: `.tmp/qa/` (вне git) — `cdp.mjs`, `pages.mjs`, `wizard.mjs` против
    `PORT=3100 npm run start`.
  - Многострочный Python или текст с апострофами в Bash heredoc ломает разбор команды:
    писать скрипт в файл через Write и запускать его.
  - Скриншоты: headless Chrome запускать из PowerShell (`Start-Process`), из Git Bash он
    молча ничего не сохраняет.
  - Service worker страниц не кэширует никогда — только `/_next/static`, иконки, картинки и две
    офлайн-страницы. При изменении `public/sw.js` менять `VERSION`.
  - Офлайн-страница — статический файл в `public/`, а не маршрут: страница приложения, отданная
    вместо другого адреса, запускает роутер, тот снова запрашивает адрес и показывает экран ошибки.
  - Переключатель «offline» в DevTools/CDP не действует на запросы service worker: офлайн
    проверять, останавливая сервер (`.tmp/qa/pwa.mjs` так и делает).
  - После удаления маршрута `tsc` падает на `.next/dev/types/validator.ts`: удалить `.next/dev`.
  - Токены писем идут после `#` и читаются в браузере (`lib/use-link-token.ts`); не возвращать
    их в query-строку. `lib/booking/tokens.ts` тянет `node:crypto` — в клиент импортировать
    `lib/booking/link-token.ts`.
  - Новая миграция: `npm run db:migrate` применяет её к рабочей базе владельца.
  - Проверки Фазы 05: `.tmp/qa/pwa.mjs` (заголовки, манифест, офлайн), `.tmp/qa/a11y.mjs`
    (структура всех страниц; с аргументом `shots` снимает `docs/screenshots`).

## NOVA Residence: постоянные инструкции

- **Источник требований** — `nova-residence/docs/brief.md` (Master Prompt + Multi-Agent
  Workflow + пять фаз). Владелец назначил Master Prompt и Multi-Agent Workflow
  постоянными инструкциями проекта. Приоритет: бриф → `nova-residence/docs/design-system.md`
  → инструкции текущей фазы → решения Lead → рекомендации субагентов.
- **Фазы**: выполняется только та фаза, на которую владелец дал явную команду. После
  фазы — отчёт и остановка. К следующей не переходить без команды.
- **Команда**: основная сессия — Lead Agent; три субагента описаны в `.claude/agents/`:
  `nova-ui` (вёрстка), `nova-motion` (интерактив и анимации), `nova-qa` (критическое
  ревью, только находит проблемы). Других субагентов не заводить. Два агента не правят
  один файл одновременно; токены, `globals.css`, `components/ui/` и архитектуру меняет
  только Lead.
- **Экономия токенов** (просьба владельца, 2026-10-05): не больше одного вызова каждого
  субагента за фазу, без параллельных копий одной роли и без повторного ревью; замечания
  ревью правит Lead. Скриншоты — только изменённых секций на 1440 и 390, не вся страница
  на всех ширинах. Проверки (typecheck, lint, build, визуальная проверка изменённого) не
  сокращать.
- **Ветки**: каждая фаза — в своей ветке `nova/phase-NN`, мерж в `main` после ревью владельца.
- **Изображения**: исходники от владельца (сгенерированы в ChatGPT) лежат в
  `nova-images-inbox/` вне git; `npm run images -- ../nova-images-inbox` пересобирает
  `nova-residence/public/images` с единой цветокоррекцией.
- **Проверка**: `npm run typecheck`, `npm run lint`, `npm run build` из `nova-residence/`.
- **Грабли**: Next.js 16 отличается от прежних версий — перед использованием API сверяться с
  `nova-residence/node_modules/next/dist/docs/`. Headless Chrome в Windows не делает окно
  уже ~500px: для мобильных скриншотов оборачивать страницу в iframe нужной ширины.

## Видимость

- **Репозиторий публичный** с 2026-10-11 (решение владельца). Всё, что попадает в любую ветку,

  изображений. Перед пушем новых файлов с настройками — проверять.
